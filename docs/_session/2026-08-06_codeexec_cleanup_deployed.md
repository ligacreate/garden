## 1. Монитор грантов

`check_grants.sh` терял код возврата `psql`. Стояло
`read ... <<<"$(psql ...)" || { log ...; exit 1; }` — и `||` относился к
`read`, а не к запросу. Недоступная база давала пустую строку, `read`
проглатывал её с кодом 0, а дальше пустые значения в `[[ -ge ]]` считались
нулями.

Итог: монитор рапортовал `WIPE detected: authenticated= web_anon=` **и
запускал восстановление грантов**, которых никто не снимал. Ровно это лежит в
хвосте прод-лога за 27.07:

```
[2026-07-27T13:00:29Z] recover: ERROR: ensure_garden_grants() failed
[2026-07-27T13:00:29Z] check: ERROR: recovery script failed
```

**Починка.** Вывод `psql` держим в переменной отдельно от `read`, код возврата
проверяем явно, значения — на численность. Пустое или нечисловое значение это
сломанный запрос, а не ноль грантов: на ноль отвечаем восстановлением, на
сломанный запрос отвечать нечем — логируем и выходим.

`ENV_FILE` и `RECOVERY_SCRIPT` сделаны переопределяемыми через env, как
`LOG_FILE` — иначе сценарии не прогнать, не трогая прод.

**Тест** `scripts/check_grants.test.sh` — восемь сценариев с подставным
`psql`, база не нужна. На версии **до** правки четыре падают, причём «база
недоступна» доходит до запуска recovery. После — **18/18**.

Выкат: `rsync` в `/opt/garden-monitor/check_grants.sh`, бэкап прежней версии
рядом (`.bak-2026-08-06`), владелец возвращён в `root:root`. Боевой прогон —
код 0 и тишина, как и положено при живых грантах. Cron на месте:
`/etc/cron.d/garden-monitor`, каждую минуту. Контрольная сумма прода совпала с
репозиторием.

schema'`. Он отработал: в логе контейнера `Schema cache loaded 57 Relations`

## 3. Фронт

Запасная запись подписки в `push_subscriptions` через PostgREST осталась со
времён, когда push-server только поднимали и эндпоинта ещё не было.
`/push/subscribe` на месте давно, таблицей владеет push-server и сам её читает
при рассылке (её **не трогали** — она живая, просто пустая). Запись из
браузера в серверную таблицу давала бы строки, за которые никто не отвечает.
Вместо молчаливого фолбэка — понятная ошибка пользователю.

Заодно убраны пять ссылок на `leader_about` — без этого дроп колонки сломал
бы сохранение профиля.

## Порядок выката и почему такой

Выкат получился **один**, как и договаривались:

1. `rsync` монитора — прод независим от FTP.
2. Один push с тремя коммитами: монитор, фронт, файл миграции. GitHub Actions
   считает прогон на push, а не на коммит, поэтому прогон один.
3. Дождались зелёного выката и `200`, проверили живой бандл.
4. Накат миграции — уже на выкаченном фронте.

Файл миграции поехал в ту же пачку сознательно: `database/**` пока не в
`paths-ignore`, а фронт выкат и так запускает — так их один, а не два.

## Не сделано: `paths-ignore`

**Правка не доехала.** В `origin/main` в `paths-ignore` по-прежнему нет
`database/**` и `migrations/**` — только `push-server/**`. Я её подготовил, но
запушить не могу: у токена нет scope `workflow`, GitHub отклоняет любой пуш,
трогающий `.github/workflows/`:

```
! [remote rejected] main -> main (refusing to allow an OAuth App to create
  or update workflow `.github/workflows/deploy.yml` without `workflow` scope)
```

Нужно добавить через веб-интерфейс, рядом с `push-server/**`:

```yaml
      - 'database/**'
      - 'migrations/**'
```

`scripts/**` туда **сознательно не идёт**: оттуда сборка зовёт
`postbuild-reset.mjs`, и молча перестать выкатывать фронт хуже, чем лишний
прогон.
