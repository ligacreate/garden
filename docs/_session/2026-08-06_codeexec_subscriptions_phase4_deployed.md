## Порядок выката

Между накатом миграции и рестартом старый код и новый индекс несовместимы:
старый `on conflict` не сработал бы, а вставка второй `active`-строки упёрлась
бы в уникальность. Поэтому шаги шли так, и окно держалось в секундах:

1. `rsync` — код на диске, сервис ещё на старом.
2. `shadow` — кик-лист поимённо (гейт).
3. Накат миграции.
4. Рестарт сразу за накатом, при условии что индекс появился.

## Что было не так

Ключом конфликта была пара `(provider, provider_subscription_id)`. Замер по
сорока шести активным строкам показал, что устойчивости в ней нет:

| что лежит в `provider_subscription_id` | строк |
| --- | --- |
| id заказа из `payment_orders` (uuid) | 27 |
| `user_id` — подстановка по умолчанию | 19 |
| настоящий id подписки Продамуса | **0** |

Продамус идентификатор подписки не присылает вовсе. Ключи двух оплат не
совпадали, `do update` не срабатывал — и вместо обновления строки появлялась
вторая, а старая оставалась `active` со своей просроченной датой.

## Как выглядит ключ теперь

Ключ идентичности — сам человек:

```sql
CREATE UNIQUE INDEX uq_subscriptions_one_active_per_user
  ON public.subscriptions (user_id) WHERE status = 'active';
```

```sql
insert into public.subscriptions (...) values (...)
on conflict (user_id) where status = 'active' do update
   set provider = excluded.provider,
       provider_subscription_id = coalesce(excluded.provider_subscription_id,
                                           subscriptions.provider_subscription_id),
       paid_until = excluded.paid_until, last_payment_at = now(), ended_at = null
```

Из трёх вариантов выбран этот, потому что только он чинит межпровайдерный
случай: у трёх человек из четырнадцати дубль собран из `prodamus` + `manual`,
и ключ `(user_id, provider)` их бы не поймал.

Прежний ключ не удалён, а **сужен до `active`-строк**. Без этого журнал
перестал бы расти: у человека с закрытым периодом повторная оплата с тем же
идентификатором упёрлась бы в уникальность со старой строкой.

Три разъехавшихся апсерта сведены в один модуль
`push-server/subscriptionJournal.mjs`. Закрытие периода теперь ищет строку по
человеку, а не по провайдеру, и ничего не пишет, если закрывать нечего.
`id` заказа в `provider_subscription_id` больше не кладём — заказы живут в
`payment_orders`.

| | было | стало |

| `active` строк / людей | 46 / 32 | **30 / 30** |
| закрытых строк | 1 | **17** |
| людей с двумя `active` | 14 | **0** |
| `active` с датой в прошлом | 15 | **0** |
| расхождений с `profiles.paid_until` | 14 | **0** |

Гасили, не удаляли. `ended_at = least(paid_until, now())` — дата, когда период
на самом деле кончился, а не момент правки. У одной строки (Ирина Петруня,
08.08) дата была в будущем — там `least` дал `now()`.

**Дата историческая**, о чём сказано в `COMMENT ON COLUMN
subscriptions.ended_at`: восстановлена задним числом, а не зафиксирована в
момент события; такие строки — `status='finished'` и `updated_at` за 06.08.

Отдельно стоит решить, нужна ли колонка-пометка для отчётов: сейчас
«историчность» живёт в комментарии к колонке, а не в самих данных. Не делала —
это уже за рамками поручения.

## Промах: этот коммит всё-таки уронил фронт

Коммит с миграцией запустил `Deploy to FTP`. Причина в том, что фаза 1
добавила в `paths-ignore` только `push-server/**`, а миграции лежат в
`database/pvl/migrations/` — и `database/**` в исключения не входит.

Выкат прошёл успешно (15 минут), в середине сайт отдавал `403` — это штатное
окно `dangerous-clean-slate`, вебрут сносится перед заливкой. Сейчас
`liga.skrebeyko.ru` отвечает `200`.

**Что стоит доделать.** Добавить в `paths-ignore` рядом с `push-server/**`:

```yaml
      - 'database/**'
      - 'migrations/**'
```

Основание ровно то же, что у фазы 1: на FTP уезжает только собранный фронт
(`dist/.`, `goroscop`, `trees`, `assets`, `favicon.png`), а SQL-миграции в
заливку не входят вообще. Иначе каждый следующий коммит с миграцией будет
ронять сайт на четверть часа впустую.

Сама эта правка тоже запустит выкат — она трогает `.github/workflows/`, а этот
путь в исключения не входит и не должен. Поэтому момент лучше выбрать не в час
пик. Не делала: решение по времени за Олей.
