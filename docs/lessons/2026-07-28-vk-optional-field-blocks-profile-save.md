# Необязательное поле уронило сохранение всего профиля

**Дата:** 2026-07-28
**Фикс:** `1eabe81` — `services/dataService.js`, `views/ProfileView.jsx`, `lib/contactNormalize.js`

## Симптом

Оля сформулировала это как «надо сделать профиль в vk необязательным полем».
При проверке оказалось, что пустой ВК везде проходит нормально, а падает
заполненный «неправильно»: человек вписывал в поле ВК своё имя кириллицей,
телефон или слово «нет» — и не сохранялся **весь профиль**. Ни имя, ни город,
ни фото, ни компетенции, ни «что могу предложить».

Отдельно коварно то, как это выглядело на экране. `UserApp.handleUpdateProfile`
делает оптимистичное обновление **до** запроса, поэтому новые значения
появлялись сразу, а тост ругался только на формат ВК. Читалось как «ну, ВК не
понравился, зато остальное сохранилось». Пропажа обнаруживалась только после
перезагрузки страницы — то есть в другой момент времени и без видимой связи с
причиной.

## Корневая причина

`dataService.updateUser` обращался с необязательным полем как с обязательным —
не по признаку «пустое / непустое», а по признаку «распознаётся / не
распознаётся»:

```js
if (hasField(updatedUser, 'vk')) {
    const normalizedVk = normalizeVk(clean.vk);
    if (normalizedVk && !isValidVk(normalizedVk)) {
        const err = new Error('VK должен быть в формате https://vk.me/username');
        err.userFacing = true;
        throw err;            // ← прерывает сборку тела PATCH целиком
    }
    dbUser.vk = normalizedVk;
}
```

`throw` стоял в середине функции, которая собирает тело `PATCH` для **всех**
колонок профиля. Отказ по одному необязательному полю отменял запись всех
остальных. При этом `VK_RE` принимает только латиницу
(`[A-Za-z0-9_.-]{2,64}`), а `normalizeVk` покорно превращает любой ввод в
`https://vk.me/<что-угодно>` — то есть кириллица гарантированно доходила до
валидатора уже в виде «ссылки» и гарантированно её не проходила.

## Почему так получилось

**Валидация необязательного поля жила в слое записи, а не в слое ввода.**
Шапка `lib/contactNormalize.js` прямо обещала UX-валидацию в форме:

```
 *   - views/ProfileView.jsx   → handleSave (UX-валидация)
```

В `ProfileView.handleSave` проверялся только Telegram. Комментарий описывал
намерение, а не код, и это расхождение никто не ловил: с точки зрения
`updateUser` всё выглядело правильно — «валидатор есть, ошибка внятная,
`userFacing` выставлен». Не хватало вопроса «а что произойдёт с остальными
двадцатью колонками, когда этот throw выстрелит».

**Понятие «обязательности» было размазано по четырём слоям, и они не
противоречили друг другу — просто ни один не отвечал за целое.** Колонка
`profiles.vk text DEFAULT ''` без NOT NULL, `isValidVk('')` возвращает `true`,
в форме написано «(необязательно)», в `utils/profileCompleteness` поля `vk` нет
вовсе. Все четыре говорили «необязательное», и все четыре были правы. Пятое
место — путь сохранения — молча говорило обратное, и именно оно решало.

**Оптимистичное обновление скрыло симптом.** Правки появлялись на экране, ошибка
касалась только ВК, а расхождение с базой становилось видно после перезагрузки.
Это отодвинуло обнаружение бага на неопределённый срок: пользователь не
связывает «пропали данные профиля» с «вчера что-то было не так с ВК».

## Как починили

**Слой-владелец — путь сохранения.** `updateUser` больше не бросает на ВК:
нераспознанную ссылку он просто не пишет, прежнее значение в базе остаётся,
остальные колонки уходят штатно. Пустая строка по-прежнему валидна, поэтому
очистить поле можно.

```js
if (hasField(updatedUser, 'vk')) {
    const normalizedVk = normalizeVk(clean.vk);
    if (isValidVk(normalizedVk)) dbUser.vk = normalizedVk;
}
```

**Слой ввода информирует, но не сторожит.** `ProfileView` считает
`vkInputInvalid` во время набора и показывает подсказку под полем: ссылку не
сохраним, остальной профиль сохранится. Непонятный ВК не подставляется в
payload — иначе оптимистичное обновление показало бы в профиле ссылку, которой
в базе нет.

**Выровняли соседний слой.** `LeaderPageView.handleSaveReviews` шлёт весь объект
профиля вместе с `vk` из базы. Пока `throw` был на месте, одна некорректная
строка `vk` заблокировала бы человеку и сохранение отзывов, и вообще любое
сохранение профиля — без возможности починить это из интерфейса. Правка в
слое-владельце закрывает и это, отдельного кода не потребовалось.

**Проверили масштаб по проду:** из 61 профиля `vk` заполнен у 16, невалидных
среди них ноль. Заблокированных не было, бэкфилл не понадобился — баг бил в
момент ввода, а не по сохранённым данным.

**Поправили комментарий**, который обещал валидацию в форме. Теперь описание
совпадает с кодом.

## Что проверить в будущем

**Сигнал первый: `throw` внутри функции, которая собирает батч.** Если функция
пишет много полей за один запрос, любой отказ в её середине отменяет всё.
Спрашивать не «правильно ли поле», а «что не сохранится вместе с ним».
Необязательное поле не имеет права отменять обязательные.

**Сигнал второй: оптимистичное обновление плюс исключение в записи.** Такая
пара всегда даёт расхождение экрана и базы, которое всплывает через
перезагрузку. Везде, где перед запросом обновляется локальное состояние, нужно
понимать, что показывается пользователю при отказе.

**Сигнал третий: нормализатор, принимающий любой ввод, перед строгим
валидатором.** `normalizeVk('Ольга')` возвращает правдоподобную ссылку, которая
затем гарантированно не проходит `VK_RE`. Если нормализатор не умеет сказать
«это не оно», проверку нужно ставить рядом с полем ввода, а не в конце пути.

**Сигнал четвёртый: комментарий, описывающий валидацию в другом файле.** Такое
утверждение стареет молча. Если шапка модуля говорит «проверяется там-то» —
это повод открыть тот файл и убедиться.

**И вопрос, с которого стоило начать:** «обязательное» для поля — это про
пустоту или про формат? Здесь ВК был необязательным по первому смыслу и
жёстко обязательным по второму, и вся путаница выросла из того, что эти два
смысла назывались одним словом.
