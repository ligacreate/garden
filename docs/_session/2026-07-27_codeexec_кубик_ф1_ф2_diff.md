## 1. Миграции (три файла, порядок строгий)

### 1.1 `migrations/2026-07-27_cube_participants_and_gate.sql`

Таблица `cube_participants (user_id PK → profiles, added_at, added_by, note)`.

**Почему таблица, а не флаг в `profiles`.** На profiles живёт permissive `profiles_update_own` (UPDATE своей строки) плюс table-level `GRANT UPDATE` для authenticated. Колоночных ограничений RLS не даёт. Значит флаг «участница Кубика» в профиле участница поставила бы себе сама одним PATCH через PostgREST. Отдельная таблица с admin-only записью закрывает это структурно.

Два хелпера в стиле `has_platform_access` (sql, STABLE, SECURITY DEFINER, фиксированный search_path):

- `is_course_staff()` — роль в (mentor, curator, admin). Существующая `is_mentor_for(uuid)` отвечает на другой вопрос — «ментор ли я вот этой ученице».
- `is_cube_participant()` — есть ли моя строка в `cube_participants`.

Политики `cube_participants`: SELECT своё, SELECT персоналу, INSERT/UPDATE/DELETE только `is_admin()`. Плюс RESTRICTIVE-гвард `has_platform_access` в command-specific форме (не FOR ALL — на FOR ALL спотыкались в phase46, он гейтит и SELECT).

**Гейт на материалы — единственное место, где трогаем общую таблицу:**

```sql
CREATE POLICY knowledge_base_cube_course_gate
  ON public.knowledge_base AS RESTRICTIVE FOR SELECT TO authenticated
  USING (
    category IS DISTINCT FROM 'Кубик ведущей'
    OR public.is_cube_participant()
    OR public.is_course_staff()
  );
```

Политика может только сузить выдачу, а первое условие пропускает все строки, у которых категория не равна названию курса — остальная библиотека не задета вообще. `IS DISTINCT FROM`, а не `<>`: у материала без категории `category` = NULL, обычное сравнение дало бы NULL и строка исчезла бы из выдачи у всех.

Откат одной строкой: `DROP POLICY knowledge_base_cube_course_gate ON public.knowledge_base;`

### 1.2 `migrations/2026-07-27_cube_cells.sql`

```sql
CREATE TABLE public.cube_cells (
    user_id uuid NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
    face smallint NOT NULL,          -- 1..6, грань = неделя
    pos  smallint NOT NULL,          -- 0..8, место в сетке
    title text NOT NULL DEFAULT '',
    body  text NOT NULL DEFAULT '',
    filled_at timestamptz,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, face, pos), CHECK (face BETWEEN 1 AND 6), CHECK (pos BETWEEN 0 AND 8)
);
```

- Колонка `pos`, а не `position`: `position` в Postgres — ключевое слово функции `position(x in y)`, в запросах читается двусмысленно.
- Первичный ключ (user_id, face, pos) — он же цель upsert из приложения.
- Триггер `trg_cube_cells_touch`: держит `updated_at` и **один раз** ставит `filled_at`, когда в ячейке впервые появился текст. Обратно не снимает — «когда добыла» это факт из прошлого.
- **`filled_at` не признак состояния.** Заполненность выводится из непустых title/body и копией нигде не хранится. Отдельная вторая запись про то же самое рано или поздно разъедется с первой — на этом уже ловили рассинхрон бейджа и процента в профиле.
- Смысл позиций (знаю / говорю / делаю / центр) живёт в коде, в базе только числа. Подписи фиксированные, меняются вместе с кодом, а не данными.

RLS: SELECT своё + SELECT персоналу; INSERT, UPDATE, DELETE — строго своё. Персоналу запись не даём: чужой кубик не редактируют. Плюс те же четыре RESTRICTIVE-гварда.

**Permissive заведены на все четыре команды осознанно.** Команда без permissive-политики в Postgres запрещена всем, запись «проходит» и трогает ноль строк, фронт показывает ложный успех. Ровно это было на `news` и превентивно закрывалось на `course_progress`. В VERIFY на это отдельная проверка V3 — считает permissive-политики по командам, ожидание четыре строки.

### 1.3 `migrations/2026-07-27_cube_grants_safety_net.sql`

Вносит `cube_participants`, `cube_cells` и два хелпера в `ensure_garden_grants()`.

**Зачем отдельным шагом — и почему без него нельзя.** RUNBOOK §1.3: Timeweb сносил кастомные GRANT'ы вскоре после DDL, два P0 за май 2026. Защита — монитор раз в минуту, порог `authenticated < 100`, авто-вызов `ensure_garden_grants()`. Но функция выдаёт права только перечисленным в ней таблицам. Не добавить туда cube-таблицы — после ближайшего wipe вся платформа восстановится, а кубик останется мёртвым с 42501, **и монитор смолчит: двумя таблицами его порог не пробить.** Это была бы ровно та тихая поломка, которую потом ищут неделю.

Тело функции взято из последней версии в репозитории (`phase45`, 2026-07-09) и дополнено четырьмя строками. Больше в теле не изменено ничего.

**Защита от дрейфа:** перед заменой pre-check проверяет, что на проде лежит ожидаемая версия (маркеры phase38/40/45). Если кто-то правил функцию мимо репозитория — миграция падает и чужие правки не затирает. Тогда снять `prosrc`, дописать те же четыре строки, пересобрать файл.

Во все три миграции добавлен обязательный `SELECT public.ensure_garden_grants();` перед `COMMIT` — RUNBOOK §1.3.

### 2.1 `services/dataService.js`

Пять методов в `RemoteApiService` и зеркальные заглушки на localStorage в `LocalStorageService` (dev-режим не должен падать):

| Метод | Что делает |
|---|---|
| `getCubeParticipantIds()` | список участниц (свою строку видит каждая, весь список — персонал) |
| `isCubeParticipant(userId)` | отмечен ли пользователь |
| `setCubeParticipant(userId, on, addedBy)` | отметить или снять, admin-only по RLS |
| `getCubeCells(userId)` | ячейки; userId передаётся явно |
| `saveCubeCell({...})` | upsert одной ячейки по первичному ключу |

Две вещи, на которые стоит посмотреть отдельно:

- **Upsert через `Prefer: resolution=merge-duplicates` кладём в `options.headers`**, а не через `returnRepresentation`: в `postgrestFetch` флаги `count`/`returnRepresentation` присваивают `headers.Prefer` уже после спреда пользовательских заголовков и затёрли бы его.
- **Пустое представление в ответе трактуем как провал записи.** Это прямая защита от той самой RLS-дыры: если permissive-политики не окажется, PostgREST вернёт 2xx и пустой массив, и без этой проверки админка отрапортовала бы «отмечено», а в базе бы ничего не было.

Плюс одна строка в общий `postgrestFetch` — опция `keepalive` (по умолчанию false), нужна автосохранению на уходе со страницы.

### 2.2 `views/CubeView.jsx` (новый)

Три экрана: шесть граней → сетка три на три → редактор ячейки. Мобильный: сетка `grid-cols-3` с квадратными плитками, редактор на всю ширину.

Автосохранение сделано слоями, потому что терять текст нельзя (женщина пишет пять–пятнадцать минут):

1. пауза в наборе 800 мс;
2. потеря фокуса любым из двух полей — сохраняем сразу;
3. `visibilitychange` в hidden и `pagehide` — сохраняем с `keepalive`, запрос переживает закрытие вкладки;
4. `beforeunload` при несохранённом — браузер спрашивает подтверждение;
5. **спасательный буфер:** если запрос не прошёл, текст уходит в localStorage и статус честно говорит «не сохранилось, текст цел». При загрузке буфер применяется только если он новее серверной версии, иначе стирается. Это страховка от потери, а не второй источник правды: при успешном сохранении запись немедленно удаляется.

Статус сохранения виден всегда: «Сохраняем…», «Сохранено», «Не сохранилось». Молчаливого «вроде сохранилось» нет.

Ни процентов, ни счётчиков, ни подсветки пустых ячеек — по правилу курса.

**Отдельно:** `getCubeCells(userId)` вызывается с явным userId. Без него у куратора и админа RLS пустил бы чужие строки, и запрос склеил бы в один кубик всех участниц.

## 5. Находка мимо задачи (не трогал, на решение)

`profiles` разрешает пользователю PATCH своей строки без колоночных ограничений, а `role` лежит там же. Из этого следует, что роль в своей строке технически самоназначаема через прямой запрос к API. На проде не проверял — это read-only recon на отдельное разрешение, и к Кубику отношения не имеет. Если подтвердится, лечится триггером-гвардом на привилегированные колонки. Записал сюда, чтобы не потерялось.
