# Семена — начисление на сервер

**Дата:** 2026-07-27
**Статус:** [ ] не начат
**Зачем:** снять последнюю привилегированную колонку `profiles` с клиента, чтобы её можно было закрыть тем же гвардом, что и роль с оплатой.

## Что не так сейчас

Баланс семян — целиком клиентский. `views/UserApp.jsx` одиннадцать раз пишет
`onUpdateUser({ ...user, seeds: (user.seeds || 0) + N })`, а это идёт в
`App.jsx#handleUpdateUser` → `api.updateUser` → `PATCH /profiles` под ролью
`authenticated`. То есть сумму назначает браузер.

Инвентаризация (строки на 2026-07-27):

| Строка | Событие | Сумма |
|---|---|---|
| 233 | пересчёт баланса при первой загрузке | итог по всем встречам |
| 357 | встреча создана | +5 |
| 395 | встреча проведена | +25 |
| 431 | встреча удалена | −5 (клампится в 0) |
| 453 | практика | +N |
| 490, 518 | материалы | +40 |
| 609 | сценарий сохранён/опубликован | +100 / +150 |
| 616, 622 | урок пройден, сценарий Лиги изучен | +20 |
| 639, 659, 687, 705 | прочие события | +N |

Плюс уже существующая RPC `public.increment_user_seeds(uuid[], integer)` —
`SECURITY DEFINER`, **без единой проверки прав**, и `authenticated` имеет на
неё `EXECUTE` (сверено на проде). То есть даже после гварда на колонку
любой залогиненный начислит себе (и кому угодно) любую сумму одним вызовом.
Сейчас ею начисляют семена со-ведущим.

## Что сделать

1. **Одно место начисления на клиенте.** Хелпер `awardSeeds(amount, reason)`
   в `UserApp`: вызывает RPC и обновляет состояние через `onProfileRefresh`
   (локально, без `PATCH`). Все одиннадцать мест переводим на него.
2. **Права на RPC.** Начисление должно быть привязано к событию, а не к
   сумме из браузера. Минимум: `increment_user_seeds` пускает только
   `is_admin()` либо начисление себе и со-ведущим по конкретной встрече,
   сумма — из справочника событий на стороне БД, а не из аргумента.
   Правильнее — новая RPC `award_seeds(p_event text, p_ref uuid)`:
   сама смотрит, что событие произошло и ещё не оплачено семенами
   (журнал начислений), сама берёт сумму. Старую после перевода
   `REVOKE EXECUTE ... FROM authenticated`.
3. **Журнал начислений** `seed_ledger(user_id, event, ref_id, amount, created_at)`
   с уникальным ключом по `(user_id, event, ref_id)` — это же чинит и
   двойные начисления, и делает баланс выводимым, а не хранимым.
4. **Пересчёт при загрузке (строка 233)** — убрать с клиента совсем: если
   есть журнал, баланс считается из него.
5. **Мелочь на потом не забыть:** `dataService.register` кладёт `seeds` в
   пост-регистрационный `PATCH /profiles`, если поле пришло в `userData`.
   Сейчас форма регистрации его не шлёт (`undefined` → в тело не попадает),
   но строку надо убрать вместе с остальными — иначе после гварда
   регистрация с непустым `seeds` упадёт 403.
