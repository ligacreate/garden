# Урок 2026-08-06: монитор грантов принимал недоступную базу за снос грантов

## Симптом

`check_grants.sh` слал тревогу `🚨 Garden GRANT WIPE detected` с **пустыми**
значениями:

```
authenticated= (expected ≥100)
web_anon= (expected ≥4)
```

и следом запускал восстановление грантов, которое, разумеется, тоже падало —
база-то недоступна. В прод-логе это выглядит так:

```
[2026-07-27T13:00:29Z] recover: ERROR: ensure_garden_grants() failed
[2026-07-27T13:00:29Z] check: ERROR: recovery script failed
```

Человек, читающий такую тревогу, думает, что у него сняли гранты и сломалось
восстановление. На деле не происходило ни того, ни другого: просто база была
недоступна.

## Корневая причина

Одна строка:

```bash
read -r AUTH_CNT ANON_CNT <<<"$(psql ... )" || { log "ERROR: psql query failed"; exit 1; }
```

`||` относится к `read`, а не к `psql`. Код возврата запроса теряется внутри
подстановки команд — снаружи виден только результат `read`. А `read` из
here-string с пустой строкой отрабатывает успешно и просто кладёт в обе
переменные пустоту.

Дальше пустота попадает в арифметическое сравнение:

```bash
if [[ "$AUTH_CNT" -ge "$AUTH_THRESHOLD" && ... ]]
```

`[[ "" -ge 100 ]]` в bash — это `0 -ge 100`, то есть ложь. Пустой ответ
неотличим от «грантов ноль», и монитор честно делает то, что положено делать
при нуле грантов: бьёт тревогу и запускает восстановление.

`set -euo pipefail` здесь не спасает: `|| { ... }` сам по себе снимает
`errexit` с этой команды.

## Почему так получилось

Две отдельные ошибки, каждая из которых по отдельности была бы безобидна.

**Первая — проверка не того.** Написать `cmd || handler` для команды внутри
`$(...)` выглядит как проверка команды, но проверяет обёртку. Это тихо: shell
не предупреждает, тесты писать было не на чем, а в норме ветка не
исполняется — она нужна ровно в тот момент, когда всё и так плохо.

**Вторая — отсутствие данных приняли за данные.** Пустая строка прошла в
числовое сравнение и получила значение «ноль». Это тот же класс, что и
подстановка по умолчанию в дублях подписок ([[2026-08-06-dubli-podpisok-neustoychivy-klyuch]]):
и там, и здесь система превращала «ответа нет» в правдоподобное значение и
принимала по нему решение.

Обе ошибки сошлись в самом неудачном месте: обработчик аварии, который сам
себе вменяемость не проверяет.

## Как починили

- Вывод `psql` держим в переменной **отдельно** от `read`, код возврата
  проверяем явно: `if ! GRANT_COUNTS="$(psql ...)"; then ... fi`.
- Значения валидируем на численность: `^[0-9]+$`. Пустое или нечисловое —
  сломанный запрос, а не ноль грантов. Логируем и выходим, восстановление
  **не** запускаем: на ноль мы отвечаем восстановлением, на сломанный запрос
  отвечать нечем.
- `ENV_FILE` и `RECOVERY_SCRIPT` сделаны переопределяемыми через env, как
  `LOG_FILE` — иначе сценарии не прогнать, не трогая прод.
- Заведён `scripts/check_grants.test.sh`: восемь сценариев с подставным
  `psql`, база не нужна. На версии до правки четыре падают.

## Что проверить в будущем

Сигнал: **`|| handler` после команды, спрятанной в `$(...)` или в конвейере.**
Проверяется не то, что кажется. Если важен код возврата конкретной команды —
присваивать её результат отдельно и проверять `if ! VAR="$(cmd)"; then`.

Второй сигнал: **пустая строка в числовом сравнении.** В bash `[[ "" -ge N ]]`
не ошибка, а сравнение с нулём. Везде, где число приходит извне, проверять
`^[0-9]+$` до сравнения — иначе «данных нет» превратится в «данных ноль», и
дальше по этому нулю будет принято решение.

Третий: **у обработчика аварии должна быть своя проверка вменяемости.** Скрипт
восстановления запускается в момент, когда что-то уже не так, — и именно
тогда важнее всего отличать «сломалось то, что я чиню» от «сломался я сам».
Спрашивать себя: а что этот код сделает, если источник данных просто
недоступен?

Четвёртый: **shell-скрипты тоже тестируются.** Здесь хватило подставного
`psql` в `PATH` и переопределяемых путей — восемь сценариев, ни базы, ни
прода. Отсутствие такой возможности и было причиной, по которой ветка аварии
никогда не проверялась.
